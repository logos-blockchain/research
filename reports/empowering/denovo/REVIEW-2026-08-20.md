# Comprehensive review — 2026-08-20

Working record, not for commit. Six review dimensions run in parallel (30 agents, 977 tool calls),
every finding adversarially verified before acceptance: **24 confirmed, 0 refuted**. Every number
below was reproduced by execution against the current tree (`1f6f802`).

Four dimensions reached the one-core basis and the whale curve independently, which is why they head
the list. Two findings — the re-strike arithmetic (M1) and the stale sybil table (C5) — were not
reached by any dimension and rest on the reproductions shown beneath them.

**Both gate suites and the JS cross-check pass** (54 de-novo, 196 current-design, 150/150 golden).
The defects below are therefore all things the gates do not test, or things the gates test *on the
wrong basis*.

## The root cause: the one-core power basis survived inside the gate suite

The branch re-based every study onto a whole four-core Pi 5 board (24,146 cand/s), and
`study.py`, `scenarios.py` and `webexport.py` all use it. **`validate.py` does not.**

| site | basis | should be |
| --- | --- | --- |
| `validate.py:64` — the shared reference draw for every gate to line ~233 | `1 / spc` = 6,037 | `4 / spc` = 24,146 |
| `validate.py:221` — the cliff gate's field | `1.0 / spc * 1000` | `4.0 / spc * 1000` |
| `power.py:56` — `minimal()` | `1.0 / spc` | correct: this is the documented lower bracket |

Measured consequence on the reference run:

```
ONE CORE (validate.py:64): transition 195   bonds 24,723
BOARD    (study/reports):  transition 196   bonds 24,707
```

The bond count barely moves (the endowment binds, not the hashrate), which is why this survived —
but the **transition epoch, the block-occupancy figures and the cliff table all move materially**,
and three published conclusions rest on the one-core values.

## Critical — published conclusions that are wrong

**C1. `denovo-report.md:99` — the block-space question is not closed; it is answered the other way.**
The report: the ×100 spike epoch "averages 190 claims a block with a peak of **240** — under a
quarter of the 1,024-transaction cap — so ordinary transactions are never crowded out, closing the
block-space question the model's §8.3 had left open."

```
one core  x100 spike: max_block_claims 240   (23% of the cap)   <- the published figure
board     x100 spike: max_block_claims 863   (84% of the cap)
```
`study.py` independently reports `fullest block 863`. At 84% of the cap the honest reading is that
block space *does* come under pressure in a spike epoch. MODEL §8.3 should be reopened, not closed.

**C2. `denovo-report.md:141` — the whale curve is a pre-correction figure, and the phase does not collapse.**
Published: "at 1× it captures 17%, at 3× 52%, at 10% **83%** and **collapses the phase from 195
epochs to 33**." At the report's own configuration (`whale_run(d, 130, whale_epoch=30, epochs=220)`):

| multiple | published | measured (5 seeds) | transition |
| --- | --- | --- | --- |
| 1× | 17% | 16.6–16.8% | 196 |
| 3× | 52% | 49.7–50.3% | 196–197 |
| 10× | **83%** | **55.5–56.1%** | **196–197 — no collapse** |

Not seed noise: the spread is under 0.7pp. "Collapses to 33" contradicts SUMMARY, `design-comparison`,
`adversarial-analysis` (which correctly carries 55% Pareto / 89% homogeneous) and the gates. The same
wrong pair survives at `design-comparison.md:76`, `PLAN.md:203` and in `variant.py`'s docstring.

**C3. `adversarial-analysis.md:85` / `SUMMARY.md:66` — the 2.80× supermajority pump is a truncation artifact.**
`pump_advantage` is a ratio of *cumulative balances*; measured over 40 of the phase's ~196 epochs it
reports how much faster the pump drained a fixed pool, not how much more it earned.

```
horizon  40 epochs -> 10%/50%/90% control: [0.44, 0.80, 2.80]   <- the published row
horizon  80 epochs ->                      [0.49, 0.86, 2.10]
horizon 150 epochs ->                      [0.52, 0.84, 1.26]
horizon 190 epochs ->                      [0.53, 0.79, 1.01]
```
Over the phase a 90% miner earns **1.01×** — essentially nothing. The claim that "a supermajority
miner can nearly triple what honest mining would have paid it" does not survive. **The minority
result is robust and slightly strengthens with horizon** (0.44 → 0.53 at 10%), so "withholding loses
money below half the field" — the load-bearing conclusion — stands unchanged.

**C4. `SUMMARY.md:88` / `adversarial-analysis.md §5` — the post-phase field is quoted in cores, on the superseded basis.**
Published: "0.4, 37 and 3,677 Pi 5-equivalents at $0.01, $1 and $100." Re-deriving the break-even
field from the same inputs:

```
P=$0.01   cores=   0.4    boards=   0.1
P=$1      cores=  36.7    boards=   9.2
P=$100    cores= 3671.3   boards= 917.8      <- published 3,677
```
Exactly 4× the board figure. The energy constant is fine (1.0125e-7 Wh/candidate = 3.645e-4 J,
consistent with `rates.py`, and $0.001359/claim checks out at 2²⁶); only the device count is on the
old basis. Either divide by four or say "cores".

**C5. The sybil table is stale in every report, and there is no code that produces it.**
No sybil/flood function exists anywhere in `empowering_denovo_sim`. Reconstructed from the engine
(100 honest/epoch, 400 epochs, retiring — the documented configuration), the baseline reproduces to
19,075 against the report's 19,082, and the denial fractions are:

| flood | current | de novo — published | de novo — measured | de novo\* — measured |
| --- | --- | --- | --- | --- |
| 2× | 48.4% | 3.5% | **4.3%** | **4.8%** |
| 5× | 88.9% | 76.2% | **79.2%** | **79.3%** |
| 10× | 96.3% | 92.8% | **94.5%** | **93.4%** |

The measured values match the *gate's own hardcoded note* exactly — so the note is right and the
reports are stale. `SUMMARY.md:68` additionally copies de novo's row into the de novo\* column.
The "order of magnitude more resistant at moderate flooding" conclusion survives (4.3% vs 48.4%).

## Major

**M1. `SUMMARY.md:102` — the recommendation compares two different arrival rates.**
"1.67% of TGE … delivers 20,300; 2% delivers 22,300 … or keep 0.5% and state about 8,000." The
8,000 is the reference rate (130/epoch); the other two are 200/epoch:

```
rate=130 (reference): 0.5% -> 7,963   1.67% -> 16,566   2% -> 17,701
rate=200            : 0.5% -> 7,676   1.67% -> 20,298   2% -> 22,325
```
At a common 130/epoch a 2% pool delivers 17,701, not 22,300 — 71% of the 25,000 ambition rather
than 89%. The recommendation to "budget roughly 2% of TGE for a 25,000-node ambition" is weaker
than stated. (The identity itself is correct: 1.67% puts implied efficiency at 14.97%.)

**M2. `adversary.py` — `two_population_run` does not reproduce the engine after the transition.**
`h_mu`/`a_mu` are computed once per epoch outside the block loop, so the post-bootstrap throttle has
no within-epoch feedback; after a burst at the transition the run collapses to **zero claims
forever** (verified to epoch 239), where the engine holds steady state. **No published figure moves**
— the pump (40 epochs) and cliff (60 epochs) experiments both end well inside bootstrap (~196) — but
the harness cannot be used over a full horizon, which is what C3 requires.

**M3. `power.py:70` — `worst()` applies a cost ratio as a rate multiplier.**
`efficiency_ratio=3.45` is USD-per-candidate (2.025e-11 / 5.864e-12), applied to a *rate*. The
docstring justifies it "since the Apple class's own candidate rate is not separately benchmarked" —
but `rates.py:39` carries it as `measured=True`:

```
Pi5 board (4c)   24,146 cand/s
Apple 10 cores  375,940 cand/s  = 15.57x a board
WORST as coded   83,304 cand/s  = 3.45x a board   -> 4.5x too weak
```
The adversarial "worst measured" case is 4.5× weaker than the best measured hardware actually is.
(The pump defence strengthens with attacker power, so this understates a *favourable* result; the
whale figures move the other way.)

**M4. `power.py:30` — three GPU claims the branch has already retracted.**
The docstring still asserts a GPU rig "would be faster per unit of cost", that "the cost estimator
carries the profile but no rate", and that "every adversarial number in these reports is therefore a
lower bound". `rates.py` now carries an estimated `gpurig` rate; the GPU is ~4× **worse** per joule;
and `adversarial-analysis.md:15` explicitly withdraws the blanket caveat and splits it. Same claims
survive on `web/profitability.html:20`.

**M5. `validate.py:288` — a gate that cannot fail.**
`check("and does not reintroduce sybil fragility", True, True, note=…)` compares `True` to `True` and
measures nothing; its note carries the only occurrence of the sybil figures in the simulator. It is
the only such gate in the suite (checked).

**M6. `MODEL.md:36` — the normative band contradicts the implementation.**
Still specifies "must lie inside the measured conversion band [11.4%, 51.9%] (elevation study) … a
triple outside the band is rejected", while `params.py` implements the redesign's own re-measured
0.15 / 0.74 with no lower bound. `denovo-report.md:205` and `design-comparison.md:101` compound it by
listing the band as never re-measured, which the same report re-measures at §4.

**M7. `variant.py:20` — the recommended design's docstring states the broken rule.**
It gives `drawable_this_epoch = draw_cap_fraction * endowment_at_epoch_start` — the whole-draw cap
that stopped the endowment ever emptying. The implemented and MODEL §8.5 rule adds the scheduled
share: `sub_pool + draw_cap_fraction * endowment`. The same docstring carries the stale "88% at epoch
20, collapsing a 195-epoch phase to 23" and "median time-to-bond of thirty-nine" (measured 43).

**M8. Superseded readings still in circulation.**
- "spikes shorten the phase" — `denovo-report.md:123`, `PLAN.md:60-61`, `PLAN.md:227`,
  `web/index.html:42`. Contradicted by the same report at line 97 and by MODEL §241.

## Addendum — the "current design" column, which no dimension reviewed

The six dimensions all pointed at the redesign. The **current-design column appears in every
comparison table and was never re-derived.** Checking it afterwards turns up three things.

**A1. The column is hardcoded, not computed.** `webexport.py:158-162` carries
`elevated_retiring: 25934`, `elevated_persistent: 5682`, `door_closes_at_100_per_epoch: 34`,
`point_of_no_return_at_100_per_epoch: 212` as integer literals with the note "measured on the
EmPoWering-simulator branch". Nothing recomputes them and no gate covers them, so they cannot drift
detectably — the same defect as the sybil table (C5) and the no-op gate (M5). Only `5,682` is pinned
anywhere, by the *other* simulator at `validate.py:865`.

**A2. The headline onboarding table compares designs at different arrival rates.** The current
figures are measured at **100 miners/epoch over 400 epochs**; every de-novo figure is at **130/epoch
over 360**. Like for like:

| current design, elevated | retiring | persistent |
| --- | --- | --- |
| 100/epoch, 400 ep — **as published** | 25,934 | 5,682 |
| 130/epoch, 360 ep — the de-novo configuration | **27,125** | **5,465** |

Small, and the conclusion ("all three onboard about the same number") holds. It slightly *strengthens*
the redesign under persistence (7,963 against 5,465 rather than 5,682) and slightly weakens it under
retirement. Same defect class as M1, in the most-read table in SUMMARY.

**A3. The closing door is a persistent-regime figure quoted without the qualifier — and this one
matters.** SUMMARY §3.2 lists the door among "three properties the current design has", giving
"epoch 270 at ten arrivals an epoch, epoch 34 at a hundred, epoch 6 at two hundred and fifty". Those
are persistent-regime numbers. Re-deriving the last cohort with ≥50% odds of ever bonding:

```
persistent : {10/ep: 286,  100/ep: 40,  250/ep: 3}    <- the published 270 / 34 / 6
retiring   : {10/ep: 399,  100/ep: 251, 250/ep: 77}
```
Under retirement the door at 100/epoch closes at **251, not 34**. The recommendation's first and
heaviest argument — "a door that shuts at epoch 34 is disqualifying" — is therefore a
persistent-regime claim presented regime-free, in a document whose organising principle is that every
headline is given at both ends.

This is the mirror image of a defect already listed: the redesign's R5 result is quoted
*retiring-only* without qualifier (M8), and the current design's worst property is quoted
*persistent-only* without qualifier. **Both omissions flatter the redesign**, which is the pattern
worth naming. Neither reverses the comparison — the door is real in both regimes and the redesign has
none — but the recommendation should rest on the retiring number too, and does not say which it uses.

(My reconstruction lands near but not exactly on the published triple, 286/40/3 against 270/34/6, so
the definition of "even odds" differs slightly from mine. That the figures cannot be reproduced from
committed code is itself A1.)
